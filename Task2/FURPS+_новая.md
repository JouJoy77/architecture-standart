# Требования к MVP депозитов и накопительных счетов

Жирной пометкой **АСЗ** отмечены архитектурно значимые требования. Численные SLO, которых не было в исходных данных, приведены как проектные гипотезы. Они не становятся критериями приёмки, пока их не подтвердят владелец продукта и эксплуатация.

| Код | Требования                         | Комментарий  |
|-----|------------------------------------|--------------|
| F   | Функциональные (Functionality)     |              |
|     | На сайте отображается перечень доступных депозитов с актуальными базовыми ставками, сроками и минимальными суммами. | Требование задания. Источник данных должен быть единым с интернет-банком и АБС. |
|     | Новый клиент может отправить с сайта заявку, указав Ф. И. О. и номер телефона, и получить подтверждение приёма. | Требование задания. На сайте не выполняется открытие продукта или идентификация клиента. |
|     | Заявка с сайта автоматически создаётся в системе кол-центра и содержит данные, необходимые оператору для обратного звонка. | **АСЗ.** Исключает ручной перенос чувствительных данных и определяет интеграцию сайта с системой кол-центра. |
|     | Оператор кол-центра видит заявку, актуальные базовые ставки и разрешённые особые условия, фиксирует результат звонка и при согласии клиента передаёт обращение в АБС по существующей интеграции. | Требование задания. Окончательное согласование особой ставки выполняется в АБС. |
|     | Действующий клиент в интернет-банке видит базовые и доступные ему персональные ставки. | Требование задания. Персональные предложения выдаются только после аутентификации. |
|     | Персональное предложение связано с идентификатором клиента, продуктом, диапазоном суммы, ставкой и сроком действия. Просроченное или отозванное предложение нельзя использовать в новой заявке. | **АСЗ.** Дополнительная детализация исходного требования: без неё нельзя однозначно проверить выбранную клиентом ставку. |
|     | Клиент интернет-банка выбирает продукт, счёт списания и сумму, после чего отправляет заявку на открытие депозита или накопительного счёта. | Требование задания для MVP. |
|     | Отправка заявки из интернет-банка подтверждается одноразовым СМС-кодом; код имеет ограниченный срок действия и число попыток. | **АСЗ.** Влияет на компонент подтверждения операций и интеграцию с СМС-шлюзом. |
|     | Система проверяет допустимость счёта списания, сумму, срок действия ставки и отсутствие повторной заявки до регистрации операции. | Дополнительное требование. Нужна защита от ошибочного или повторного открытия продукта. |
|     | Заявка и использованная версия ставки сохраняются до передачи в АБС; повторная доставка не создаёт дубликат. | **АСЗ.** Дополнительное требование для надёжной асинхронной интеграции. |
|     | Менеджер депозитного бэк-офиса получает заявку в АБС, проверяет и подтверждает условия по действующему процессу. | Граница MVP: ручная обработка в бэк-офисе сохраняется. |
|     | Сотрудник кредитного бэк-офиса вводит в своём разделе АБС расчётные параметры и согласует риск, а сотрудник депозитного бэк-офиса формирует и публикует итоговую версию ставки. Подразделения не видят закрытые данные друг друга. | **АСЗ.** Переносит нынешнее согласование из Excel и почты в АБС, не нарушая действующее разделение доступа. |
|     | После подтверждения ставки и после открытия депозита клиент получает отдельные СМС-уведомления. | Требование задания. Отправка не должна блокировать основную операцию. |
|     | После подтверждения условий менеджер бэк-офиса открывает депозит или накопительный счёт в АБС по действующему процессу. АБС возвращает номер продукта и итоговый статус либо обоснованный отказ. | В MVP ручное решение сохраняется, но клиентский сценарий должен заканчиваться не только согласованием ставки, а открытием продукта. |
|     | Решение сотрудника, открытие продукта и другие изменения, произошедшие в АБС после первоначальной регистрации заявки, доставляются в онлайн-контур без потери и без прямого опроса таблиц АБС клиентскими системами. | **АСЗ.** Закрывает отложенную часть процесса: решение может появиться через минуты или часы после исходной команды. |
|     | Клиент видит в интернет-банке текущий статус заявки и итоговые параметры открытого продукта. | Дополнительное требование. Снижает обращения в кол-центр и делает асинхронный процесс понятным. |
|     | Для каждой заявки ведётся аудит смены статусов, согласования ставки, подтверждения СМС-кодом и технических повторов доставки. | **АСЗ.** Дополнительное требование для расследования спорных банковских операций. |
| U   | Удобство использования (Usability) |              |
|     | Формы сайта и интернет-банка соответствуют действующей дизайн-системе банка, используют привычные цвета, термины и элементы управления. | Требование задания. |
|     | Клиент проходит оформление по пошаговому сценарию с видимым прогрессом, итоговыми условиями и явным подтверждением перед отправкой. | Особенно важно для основной возрастной аудитории банка. |
|     | Обязательные поля валидируются до отправки; ошибки объясняют, что исправить, и не очищают уже введённые данные. | Дополнительное требование, уменьшающее число незавершённых заявок. |
|     | Интерфейс поддерживает клавиатурную навигацию, масштабирование до 200 %, достаточный контраст и подписи для экранных дикторов. | Дополнительное требование доступности для пожилых и слабовидящих клиентов. |
|     | На каждом этапе клиент видит статус: заявка принята, ожидает обработки, ставка подтверждена, депозит открыт или требуется действие. | Необходимо из-за асинхронной обработки MVP. |
|     | Текст СМС содержит назначение кода или уведомления, но не раскрывает полные реквизиты счёта и иные лишние персональные данные. | Баланс понятности и конфиденциальности. |
| R   | Надёжность (Reliability)           |              |
|     | Клиентские функции сайта и интернет-банка, а также новые сервисы депозитного контура доступны не менее 99,9 % календарного времени в месяц, исключая согласованные окна обслуживания. | **АСЗ.** Прямое требование задания. Для 30-дневного месяца это не более 43 мин 49 с недоступности. |
|     | Отказ одного экземпляра приложения или одного сервера не прерывает приём новых заявок. | **АСЗ.** Требует нескольких экземпляров и балансировки. |
|     | При сбое основного ЦОД депозитный контур восстанавливается в резервном ЦОД: предлагаемые RTO - 30 минут, RPO - 5 минут. | **АСЗ.** Это рабочие показатели для проектирования; их нужно согласовать и подтвердить испытанием переключения. |
|     | Принятая заявка не теряется при недоступности АБС, системы кол-центра или СМС-шлюза: доставка возобновляется автоматически. | **АСЗ.** Определяет применение очереди, повторов и очереди недоставленных сообщений. |
|     | Все команды создания заявки и изменения статуса идемпотентны по уникальному идентификатору операции. | **АСЗ.** Исключает дубли при сетевых повторах. |
|     | При недоступности источника ставок отображается последняя успешно полученная версия с отметкой времени; просроченная ставка не может быть использована для оформления. | Дополнительное требование для безопасной деградации. |
|     | Резервное копирование и восстановление БД новых сервисов проверяется не реже одного раза в квартал. | Дополнительное эксплуатационное требование. |
|     | Сбои интеграций, рост очередей, ошибки СМС и рассинхронизация статусов обнаруживаются мониторингом и создают оповещение дежурной команде. | **АСЗ.** Без наблюдаемости заявленная доступность неуправляема. |
| P   | Производительность (Performance)   |              |
|     | Для чтения списка продуктов, ставок и статуса заявки предлагается серверный SLO: не более 500 мс для 95 % запросов и не более 1 с для 99 % запросов. | **АСЗ.** Превращает пожелание "в миллисекундах" в проверяемый показатель; сетевое время клиента не включается, значения требуют согласования. |
|     | Для приёма онлайн-заявки предлагается серверный SLO не более 2 с для 95 % запросов; длительная обработка в АБС выполняется асинхронно. | **АСЗ.** Это открытый вопрос: две секунды буквально не соответствуют пожеланию бизнеса об отклике "в миллисекундах". Порог нужно согласовать до оценки и зафиксировать отдельным решением. |
|     | Архитектура новых stateless-компонентов допускает горизонтальное масштабирование без изменения кода. | **АСЗ.** Прямое требование задания. |
|     | Чтение ставок не создаёт онлайн-нагрузку на Oracle-БД АБС и остаётся доступным при её временном отказе. | **АСЗ.** Устраняет риск для перегруженной АБС. Конкретный механизм хранения выбирается в ADR. |
|     | Нагрузочные испытания проводятся для прогнозного пика маркетинговой кампании с согласованным запасом; профиль нагрузки фиксируется до испытаний. | В исходных данных нет чисел по трафику, поэтому TPS и коэффициент запаса должны появиться после прогноза бизнеса, а не задаваться произвольно. |
|     | Очередь заявок должна поглощать кратковременный пик и сохранять сообщения до восстановления потребителя; отставание обработки контролируется отдельным SLO. | **АСЗ.** Защищает АБС от всплеска онлайн-заявок. |
| S   | Поддерживаемость (Supportability)  |              |
|     | Для новых серверных компонентов должна быть назначена команда, способная разрабатывать и сопровождать их круглосуточно: с резервированием специалистов, обучением и дежурной сменой. | **АСЗ.** Нескольких Java-разработчиков в команде АБС недостаточно для поддержки нового контура, брокера и двух ЦОД. |
|     | Технологии новых компонентов должны быть совместимы с существующими платформами и компетенциями банка. Выбор, требующий найма или обучения, сопровождается ресурсным планом. | Ограничение задания. Java/Spring Boot и MS SQL рассматриваются как доступный вариант, но фиксируются уже в ADR. |
|     | Интеграционные контракты поддерживают надёжную асинхронную доставку для новых компонентов и совместимый синхронный интерфейс для старого интернет-банка. | **АСЗ.** Банк предпочитает Kafka, но выбор брокера относится к архитектурному решению; унаследованная платформа интернет-банка с Kafka несовместима. |
|     | API и события версионируются; для них ведутся OpenAPI/AsyncAPI-контракты, схемы данных и правила совместимости. | Требование задания о документации для расширения системы. |
|     | Компоненты поставляются через автоматизированный конвейер с модульными, интеграционными и контрактными тестами. | Дополнительное требование для безопасных независимых изменений. |
|     | Логи имеют correlation ID заявки, единый формат и маскирование персональных данных; метрики и трассировки доступны службе сопровождения. | **АСЗ.** Нужны для сквозной диагностики без утечки данных. |
|     | Бизнес-параметры продуктов, сроки действия ставок, лимиты СМС и таймауты интеграций изменяются конфигурацией без пересборки приложений. | Снижает время выпуска изменений и число обращений к подрядчикам. |
|     | Для новых сервисов подготовлены эксплуатационные инструкции, схема владения, порядок аварийного переключения и регламент обработки очереди ошибок. | Дополнительное требование для передачи решения в сопровождение. |
|     | Проектный профиль хранения: заявки и бизнес-аудит хранятся 5 лет после завершения процесса, технический аудит интеграций - 1 год, оперативные логи - 90 дней. | **АСЗ.** Это измеримые стартовые значения, а не ссылка на неизвестную "политику банка"; до запуска их подтверждают ИБ, юристы и владелец данных. |
| +R  | + Ограничения (Restrictions)       |              |
|     | Интернет-банк остаётся монолитом ASP.NET MVC на .NET Framework 4.5 и MS SQL; изменение ядра подрядчика в MVP не планируется. | **АСЗ.** Ограничение текущей платформы и срока MVP. Существующая интеграция платежей с АБС остаётся за границей проекта. |
|     | В новом депозитном процессе онлайн-каналы не обращаются напрямую к таблицам Oracle и не зависят от синхронного ответа АБС. | **АСЗ.** Защищает перегруженную АБС и отделяет новый поток от унаследованного прямого доступа интернет-банка к её БД. |
|     | АБС остаётся системой учёта банковского продукта, решения сотрудника, открытого счёта и проводок; её стек - Delphi, PL/SQL и Oracle. Сервис заявок хранит факт приёма и клиентское представление статуса. | **АСЗ.** Разделяет ответственность систем и устраняет двусмысленность "двух источников истины". |
|     | До завершения MVP заявку подтверждает менеджер депозитного бэк-офиса в АБС; полная автоматизация относится к годовому целевому состоянию. | Ограничение границы первой поставки. |
|     | Новый клиент после заявки на сайте обязан пройти очную идентификацию в отделении. | Регуляторное условие, прямо заданное в кейсе. |
|     | Персональные данные и банковская тайна шифруются при передаче TLS 1.2 или выше и в хранилищах; доступ предоставляется по минимально необходимым ролям. | **АСЗ.** Дополнительная конкретизация требования защиты чувствительных данных. |
|     | Секреты и ключи не хранятся в коде и конфигурационных файлах приложений; операции с чувствительными данными протоколируются. | Дополнительное требование безопасности. |
|     | Сотрудники депозитного и кредитного направлений не получают прямого доступа к данным друг друга. | **АСЗ.** Существующее требование информационной безопасности должно сохраниться после цифровизации. |
|     | Для хранения и обработки персональных данных соблюдаются применимые требования российского законодательства и внутренние политики банка; точный перечень контролей подтверждает служба ИБ. | Дополнительное ограничение. Из задания нельзя достоверно вывести полный набор нормативных актов и сертификационных требований. |
|     | АБС из-за единой Oracle-БД масштабируется только вертикально; нагрузка регулируется очередями, пакетной обработкой и ограничением параллелизма. | **АСЗ.** Технологическое ограничение из задания. |
